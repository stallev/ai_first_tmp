# Model routing & delegation

You are the ORCHESTRATOR. You classify, check readiness, implement ready tasks, delegate only when it pays, and integrate.
Models are pinned in `.cursor/agents/*.md` (Claude Code: generated `.claude/agents/*.md`). Routing = choosing the subagent.
Never spawn a separate "router" agent.
Canon: [`docs/meta/ai_agent_model_routing.md`](docs/meta/ai_agent_model_routing.md).

## 0. Model map (reference — do not override in prompts)

| Role | Model | Why |
|---|---|---|
| Orchestrator (chat) | Composer 2.5, NOT fast (set in the model picker) | Writes code for ready tasks; same model as `implementer`, so delegating a ready task only adds a cold start |
| `implementer` | `composer-2.5[fast=false]` | Context isolation / parallel steps only (§2) |
| `architect` | `grok-4.7[effort=high,fast=false]` | Spec-gap (fix docs) and plans; errors here are the most expensive |
| `reviewer` | `grok-4.7[effort=high,fast=false]`, readonly | The single review gate per commit unit (§6) |
| Search | built-in Explore | Already uses a fast cheap model |

Stay inside the Cursor Models pool (Grok 4.x, Composer 2.5). Do not route to third-party models.

**Claude Code:** same roles, same rules. Subagents come from `.claude/agents/*.md`, generated by `npm run rules:sync` from `.cursor/agents/*.md` (Grok → `opus`, Composer → `sonnet`, `readonly` → read-only tools). Call them with the `Agent` tool (`subagent_type: "reviewer"` / `"architect"` / `"implementer"`); search — built-in `Explore`.

## 1. Classify + Definition of Ready (one line, no extra reasoning)

Output: `Tier: T0|T1|T2|T3 — reason (≤10 words) · CU: P{N}-CU{k}|none`

**Quality profile** ([`docs/meta/project_quality_profile.md`](docs/meta/project_quality_profile.md); none yet → `standard`) sets how much of DoR applies — D2 paths, D3 DoR: `prototype` — no DoR, a task is Goal + Acceptance; `lean` — the orchestrator checks items 1–4 and 6 inline, item 6 per D2; `standard` / `strict` — all items.

**Definition of Ready (DoR)** — check by reading only the linked sections, no repo exploration:
1. Task links to spec / contract / ADR / PRD **sections** (`§N.M`), and they open.
2. Acceptance is testable and states the expected outcome.
3. Files / area are named.
4. No `TBD` / open questions in the linked sections (`Open questions` empty or not blocking).
5. Library APIs match the pinned version (`Проверено по` in the doc).
6. Paths H / N / S are described where triggers require them — canon: [`documentation_creation_registry` §2.3.2a](docs/meta/documentation_creation_registry.md). Short form: **H** — any observable behavior change; **N** — external input, mutation / state transition, fallible I/O, possibly-missing data; **S** — sensitive zone, user/role-scoped data, user-data mutation / PII / secrets / session, new public endpoint / upload / redirect / webhook. Exempt: copy/CSS, docs-only, tooling, behavior-preserving refactor, presentational component.

| Tier | Signal | Who writes code | Subagent |
|---|---|---|---|
| T0 Trivial | 1–2 files, ≤~40 lines, intent unambiguous, outside sensitive zones | orchestrator | none |
| T1 Ready | DoR passes | orchestrator | `implementer` only per §2 isolation rule |
| T2 Spec gap | DoR fails; new feature without plan; new dependency; data model / API contract change; non-obvious bug after 1 failed attempt | orchestrator, **after** docs are fixed | `architect` (`spec-gap` or `plan`) |
| T3 Risky | Auth, payments, permissions, secrets, live-data migration, destructive ops, breaking public API, **any S trigger** | as T1/T2 | `reviewer` mandatory; task is its **own CU** |

Sensitive zones — same list as `agent-code-review-subagent.mdc` § Sensitive zones.

Rules of thumb:
- Unsure between two tiers → pick the LOWER one; escalation (§4) corrects it. Exception: an S trigger is never downgraded below T3.
- Questions/explanations with no code change: answer yourself, no subagent.
- Codebase search: use the built-in Explore subagent, not `architect`.

## 2. Delegate only when it pays

The orchestrator implements T0/T1 and T2 after spec-gap itself. Spawn a subagent ONLY if at least one is true:
- DoR fails → `architect` spec-gap (docs only, no code).
- The work would add >~20k tokens of noise to this context (exploration, logs, long diffs) → `implementer` / Explore.
- Independent steps with non-overlapping `Files` can run in parallel → `implementer` per step.
- This context is near ~200k tokens → `implementer` with plan path + step, or a new chat.
- Commit-unit review (§6) → `reviewer`.

Do NOT spawn for: T0 tasks; ready tasks that fit this context; sequential steps touching the same files; anything finishable in ≤3 tool calls.
Each subagent starts cold and re-reads files — over-splitting costs more than it saves.

**Phase DoR audit:** before the first task of a phase, ONE `architect` spec-gap call checks DoR for all tasks in `P{N}_tasks.md` and fixes the docs (profile D3 `standard` / `strict`; `lean` — the orchestrator self-audits inline; `prototype` — none). Ad-hoc spec-gap later — only for gaps found mid-task.

## 3. Handoff contract

- **spec-gap:** `architect` verifies current docs (Context7 / official docs), edits only `docs/**` (spec / contract / ADR / PRD) and the task line in `P{N}_tasks.md`, follows source-of-truth order in `project-context.mdc`, records changed decisions in an ADR. Returns ≤15 lines: changed paths + DoR items closed.
- **plan (T2 multi-step):** `architect` writes `.cursor/plans/<task-slug>.md`. Every step: `Goal` · `Files` · `Acceptance` · `Tier` (T1 by default). When delegating, pass the plan PATH + step number(s), not the conversation.
- Subagents return ≤15 lines: what changed, files touched, check results, open issues.

## 3a. Commit units (CU)

Planned in advance in `P{N}_tasks.md` § Commit plan ([`phase_tasks.template.md`](docs/meta/phase_tasks.template.md)).

- CU = one logical commit: several T0/T1 tasks on one topic **or** one T2 task. **T3 = always its own CU.**
- Target ≤ ~400 hand-written lines per CU; larger → split at phase planning.
- CU header = commit subject `type(scope): subject`; plus `Review: reviewer|diff-only`.
- A task outside any CU (ad-hoc small fix) is **not** committed on its own: it stays in the working tree until a CU boundary or an explicit user request.

## 4. Escalation ladder

1. Acceptance fails → retry ONCE with the exact error.
2. Fails again → `architect` diagnoses and amends the spec / plan (does not write the code).
3. Re-apply the amended step (orchestrator or `implementer`).
4. Still failing → stop and ask the user. Never loop.

## 5. Cost hygiene (always)

- Never request `-fast` variants, `xhigh` effort or 500k-context variants unless the user explicitly asks.
- Keep any single context under ~200k tokens: beyond that Grok 4.7 bills at 2x. Start a new chat or delegate instead.
- Read files by explicit path; do not re-read files already in context.
- Prefer targeted edits over rewriting whole files.
- When a task is done or the context is mostly stale, suggest starting a new chat.

## 6. Review & commit at the CU boundary

- **One gate per CU** — [`agent-code-review-subagent.mdc`](agent-code-review-subagent.mdc): runtime code in the CU → `reviewer` (protocol 2a→2b→2c, Paths H/N/S as expected shape) — which CUs need it depends on profile D6 (`agent-code-review-subagent.mdc` § Depth); docs / `.mdc` / tests / tooling only → `diff-only` by the orchestrator.
- **Auto-commit** — [`agent-commit-pipeline.mdc`](agent-commit-pipeline.mdc): when the last task of a declared CU is done, VERIFICATION is green and `reviewer` has no blockers (≤1 delta re-review), commit without asking. Never push, `--amend`, `--no-verify`; never stage `.env*` / secrets. Blocker remains → stop and report.
- **Do not** enable IDE Agent Review on every save/commit as a substitute for this contract.
