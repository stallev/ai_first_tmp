# React state management guidelines — Pulse

**Stack:** React 19, Next.js **16.4** App Router  
**Related:** [ai_react_hooks_guidelines.md](./ai_react_hooks_guidelines.md) §11 Memoization, §14 `useSyncExternalStore`

---

## 1. When to reach for what

| Need | Use |
|------|-----|
| Local component state | `useState` |
| Related state + transitions in one component/feature | `useReducer` |
| Small, rarely-changing value shared by a subtree (theme, auth session) | `useContext` (+ `useReducer` for the dispatch side) |
| Cross-cutting client state shared across many routes/components, simple API | **Zustand** |
| Cross-cutting client state with complex async orchestration, normalized entities, or an existing team convention around actions/reducers | **Redux Toolkit** |
| Server data (fetched from DB/API) | Server Components / DAL — **not** a client store; see [`ai_data_fetching_patterns.md`](../nextjs/ai_data_fetching_patterns.md) |

Default to the top of this table. Reach for Zustand/Redux only for state that is genuinely cross-cutting — most features need nothing beyond `useState`/`useReducer` + Server Components.

---

## 2. `useReducer`

- **One reducer per unrelated concern** — a mega-reducer handling unrelated action unions (form + modal + list) breaks single-responsibility; split into separate `useReducer` calls per concern.
- **Action describes what happened, not the computed result** — `{ type: 'ITEM_ADDED', item }`, not `{ type: 'SET_ITEMS', items: [...state.items, newItem] }`. The reducer computes the transition; callers shouldn't need to know reducer internals.
- **Expensive initial state → third `init` argument** — `useReducer(reducer, rawData, init)`, not `useReducer(reducer, computeInitialState(rawData))`; `init` runs once on mount instead of on every parent render.
- **Reducers must stay pure** — never mutate `state` or perform side effects (`fetch`, `state.items.push`) inside a reducer; React (concurrent mode) may invoke a reducer more than once per dispatched action.

---

## 3. `useContext`

- **Wrap `useContext(X)` in a custom hook** (`useAuth()`) that throws a clear error when the Provider is missing, instead of calling `useContext` directly in every consumer with repeated null-checks.
- **Split by domain** — one context per concern (`ThemeContext`, `AuthContext`, `CartContext`), not one mega-context holding unrelated domains; a single context re-renders every consumer on any field change.
- **Split state from dispatch** — separate `StateContext` and `DispatchContext` (the `dispatch` reference from `useReducer` is stable) so components that only dispatch never re-render on state changes.
- **Memoize the Provider `value`** — see [`ai_react_hooks_guidelines.md`](./ai_react_hooks_guidelines.md) §11.
- **Not a substitute for a selector-based store** under high update frequency — reach for `useSyncExternalStore` or Zustand/Redux instead (§1).
- Context requires `'use client'`; Server Components cannot call `useContext` — pass data via props instead.

---

## 4. Redux Toolkit

- **Narrow selectors** — `useSelector(state => state.cart.totalPrice)`, not `useSelector(state => state.cart)`; for derived/expensive values use `createSelector`. A narrow selector subscribes the component only to the field(s) it reads.
- **Normalize collections** — `{ byId: Record<id, Entity>, allIds: id[] }` (or `createEntityAdapter`) instead of searching/updating a nested array with `.find()`/`.map()` (O(n)); normalized state gives O(1) lookup/update and no duplicated entities.
- **One `createSlice` per domain** (`userSlice`, `cartSlice`, `themeSlice`) — not one mega-slice; independent slices are independently testable.
- **`createSlice`'s "mutating" syntax**, not hand-written `switch(action.type)` + spread reducers or manual action creators/types — Immer converts the mutating syntax to an immutable update under the hood.
- **`createAsyncThunk` + `extraReducers`/`builder.addCase`** for async calls — not manual `loading`/`error` `useState` around each call; auto-generated `pending`/`fulfilled`/`rejected` actions standardize status handling.
- **RTK Query** (`createApi` + autogenerated `useGetXQuery` hooks) for server data fetched from the client — not a hand-rolled `useFetch` + manual cache/dedup layer; built-in caching, dedup, and tag-based invalidation.
- **`configureStore({ reducer: {...} })`**, not manual `createStore` + `applyMiddleware`/`compose` — wires up DevTools, `redux-thunk`, and dev-mode mutation/serializability checks automatically.
- **Typed `useAppDispatch`/`useAppSelector`** (`TypedUseSelectorHook<RootState>`) defined once, not untyped `useDispatch`/`useSelector` ad hoc per component.

---

## 5. Zustand

- **Per-field selectors** — `useStore(state => state.count)`, not `const { count, user, theme } = useStore()`; without a selector the component subscribes to the whole store and loses Zustand's main advantage over plain Context.
- **Actions co-located with the state they mutate** (`addItem: (item) => set(state => ({...}))` as a store field) — Zustand's model favors state+behavior in one store, unlike Redux's action/reducer separation.
- **Multiple small stores per domain** (`useCartStore`, `useThemeStore`, `useAuthStore`) — not one giant global store; lower coupling, easier isolated testing.
- **`get()` inside actions for current state**, not a value captured in the action's closure — the store lives outside the render cycle, so closures over `set`/outer variables can go stale; `get().count` always reads the live value.
- **Derived values via an external selector function**, not a getter field on the store object — getters aren't serializable, which breaks the `persist` middleware's JSON serialization.
- **Curried creator with middleware**: `create<T>()((set, get) => (...))`, not `create<T>((set) => (...))` — the extra call is required for TypeScript to propagate the state type correctly through `persist`/`devtools` wrappers.
- **`persist` + `skipHydration`** — guard first-render reads of `localStorage`-restored values (manually rehydrate after mount, or gate rendering until hydrated); the server has no `localStorage`, so unguarded reads cause a hydration mismatch.

### 5.1 Next.js App Router — no server-side singleton

**Critical:** a module-level singleton store (`export const useStore = create(...)`) used the same way on the server leaks one user's state into another user's response — the server is shared across requests, the browser is not.

- Client-only global stores (theme, UI toggles with no per-user sensitivity) may stay a module-level singleton **only inside Client Components** (never imported into server code).
- Any store holding per-request/per-user data must use a **store-per-request** pattern: create the store instance inside a `useRef` in a Provider component (low-level `useStore(store, selector)` API), so each mount gets an isolated instance.
